## Objetivo

Realizar auditoria técnica para identificar a causa raiz do travamento (Crash) no contêiner de produção do Railway ao tentar baixar fotos compactadas em ZIP e documentar as diretrizes/cuidados para as próximas implementações de infraestrutura e arquitetura de downloads.

## Diagnóstico Técnico (Causa Raiz)

O crash observado no contêiner do Railway logo após a requisição para `/api/fotos/download_zip.php` deve-se a dois fatores principais:

1. **Monotarefa do Servidor Embutido do PHP (`php -S`):**
   - O servidor embutido do PHP é single-threaded por padrão. Ao processar downloads e compressões sequenciais pesados de imagens do R2 dentro da mesma rota HTTP síncrona, o servidor fica bloqueado e impossibilitado de responder a qualquer outra requisição.
   - Isso faz com que os *health checks* de integridade do Railway falhem por falta de resposta rápida (timeout), levando o Railway a forçar o reinício do contêiner (status **Crashed**).

2. **Exaustão de Recursos (RAM/Disco):**
   - A geração síncrona de arquivos ZIP pesados carrega dados temporários de arquivos para a memória RAM e disco. A chamada direta de `readfile($tmpZip)` sob buffers ativos pode extrapolar o limite físico de memória do contêiner (comumente 512MB), causando a morte imediata do processo PHP pelo kernel (*Out of Memory* - Exit Code 137).

## Diretrizes e Cuidados para Próximas Implementações

Para garantir a robustez e estabilidade contínua do sistema CriaVibe nas próximas etapas de desenvolvimento, foram consolidados os seguintes critérios arquiteturais:

### 1. Parar de usar `php -S` em Produção (Urgente)
- O servidor embutido do PHP CLI deve ser removido de produção. 
- A solução definitiva é a substituição por uma infraestrutura adequada utilizando **Apache** ou **Nginx + PHP-FPM**, garantindo concorrência nativa por múltiplos workers para que o servidor não congele durante tarefas demoradas.

### 2. Transformar o Download de ZIP em Processo Assíncrono (Correto)
- O processamento de downloads e compressões pesadas não deve ser feito diretamente dentro da rota HTTP síncrona `/api/fotos/download_zip.php`.
- O fluxo de arquitetura assíncrona ideal deve ser:
  1. O usuário clica em **"Baixar ZIP"**;
  2. O backend cria uma tarefa no banco de dados / fila e responde rapidamente: *"preparando download"*;
  3. O **Worker** processa a geração do ZIP em segundo plano;
  4. O worker salva o arquivo ZIP resultante no Cloudflare R2;
  5. O usuário baixa o ZIP pronto por meio de um link temporário direto do R2.

### 3. Utilizar JSZip no Navegador Apenas como Alternativa
- A geração de ZIP no client-side com JSZip é viável para tirar a carga do servidor, mas deve ser mantida apenas como uma alternativa para poucos arquivos (galerias pequenas/médias).
- Para galerias grandes, o processamento client-side não é a solução principal, pois pode travar navegadores, falhar em celulares de baixa performance e expor fluxos adicionais de URLs no frontend.
