# Upload de fotos e capa: R2_ACCOUNT_ID errado no Railway — 09/09/2026

Diagnostico e correcao da falha total de envio de imagens: fotos e capa de
apresentacao, ambas recusadas em 100% das tentativas. **Resolvido e validado em
producao em 09/09/2026.**

## Sintomas

Dois erros diferentes, que pareciam problemas separados:

| Onde | Mensagem |
| --- | --- |
| Capa (`upload_capa.php`, servidor -> R2) | `Falha ao salvar o arquivo no Cloudflare R2. Verifique as credenciais e o bucket.` |
| Fotos (navegador -> R2 via URL assinada) | `Enviadas 0 de 3. Motivo: Failed to fetch` |

A primeira mensagem apontava para credencial e bucket. Ambos estavam corretos, e
foi por ali que o tempo se perdeu.

## Causa raiz

**O `R2_ACCOUNT_ID` configurado no Railway era de outra conta.**

| Origem | Valor | Host respondendo |
| --- | --- | --- |
| Railway (producao) | `e0bedce3…ebc5 (de outra conta)` | alerta fatal de TLS, `curl exit 35` |
| `.env` local (correto) | `a0ffb4dd…cd61` (o do `.env`) | `HTTP 400` — normal |

O account id monta o hostname do endpoint S3:
`https://<account_id>.r2.cloudflarestorage.com/<bucket>`.

Quando o id nao corresponde a uma conta real, **a Cloudflare recusa o handshake
TLS** em vez de responder um erro HTTP. Nao ha requisicao para autenticar, nao ha
codigo de status, nao ha corpo de resposta. Por isso nenhuma troca de credencial
resolvia: o problema acontecia uma camada abaixo da autenticacao.

Isso explica os dois sintomas de uma vez:

- **servidor:** `curl` devolve `TLS connect error: error:0A000410:SSL
  routines::ssl/tls alert handshake failure`;
- **navegador:** a URL assinada e montada com o mesmo host inexistente, e o
  `fetch` morre antes de qualquer resposta — que e exatamente o que o
  `Failed to fetch` significa.

### O que foi descartado, com evidencia

Antes de chegar ao account id, cada camada suspeita foi testada de fora do app,
com as credenciais do `.env`:

| Verificacao | Resultado |
| --- | --- |
| `PUT` assinado no bucket | `200` |
| `HEAD` assinado | `200` |
| `GET` pela URL publica | `200` |
| `GET` de objeto inexistente | `404` (acesso publico ligado) |
| `DELETE` | `204` |
| Preflight `OPTIONS` dos tres origins | `204` com `Access-Control-Allow-Origin` e `Allow-Headers: content-type` |
| TLS 1.2 e TLS 1.3 contra o endpoint correto | negociam normalmente |
| Endpoint correto aberto no navegador do usuario | XML `InvalidArgument` — rede local alcanca o R2 |

Conta, bucket, credencial, permissao do token, acesso publico e CORS: todos
corretos o tempo todo.

### Como o account id foi isolado

A hipotese surgiu ao notar que **os dois caminhos falhavam antes de receber
resposta**, e o unico elemento comum entre eles e o hostname do endpoint. O teste
que fechou o caso:

```bash
# account id correto
curl -o /dev/null -w "%{http_code}\n" https://<id-correto>.r2.cloudflarestorage.com/
# -> 400

# account id com um caractere trocado
curl -o /dev/null -w "%{http_code}\n" https://<id-errado>.r2.cloudflarestorage.com/
# -> 000, exit 35, alerta fatal de TLS
```

## Correcao aplicada

`R2_ACCOUNT_ID` no Railway trocado para o account id da conta correta — o mesmo
que ja estava no `.env` local. O redeploy automatico restabeleceu o envio de
fotos e de capa sem nenhuma outra alteracao.

## Leitura rapida do erro

| Sintoma | Causa provavel |
| --- | --- |
| `ssl/tls alert handshake failure` no servidor | `R2_ACCOUNT_ID` errado — host de conta inexistente |
| `Failed to fetch` no navegador, com o servidor tambem falhando | idem: a URL assinada usa o mesmo host |
| `Failed to fetch` no navegador, servidor funcionando | politica de CORS do bucket |
| `401 Unauthorized` | `R2_ACCESS_KEY_ID` inexistente ou `R2_SECRET_KEY` errada |
| `403 SignatureDoesNotMatch` | o par access key / secret nao confere |
| `403 AccessDenied` | token sem permissao de escrita (precisa Object Read & Write) |
| `403 NotEntitled` | R2 desabilitado na conta |
| `404 NoSuchBucket` | `R2_BUCKET_NAME` errado |
| `403` na URL publica | acesso publico (`r2.dev`) desligado |

A tabela anterior, com o historico das quatro camadas resolvidas em 05/09, esta
em [`trabalho_05_09_2026.md`](trabalho_05_09_2026.md).

## Mudancas de codigo

Nenhuma delas era necessaria para resolver a falha — a correcao foi a variavel.
Todas existem para que o proximo erro seja legivel em vez de virar uma cacada.

### `api/config.php`

`env_r2()` apara as cinco variaveis do R2 antes de virarem constante. Um espaco
ou quebra de linha colado no painel do Railway e invisivel no campo e produz
exatamente o mesmo host invalido. `R2_ACCOUNT_ID` virou constante propria.

### `api/lib/R2Storage.php`

- `lastError()` e `lastStatus()` expoem o motivo real e o codigo HTTP da ultima
  operacao. O XML de erro do R2 e traduzido para a causa concreta e a acao
  correspondente. Antes o metodo devolvia so `true`/`false`, e seis situacoes
  distintas chegavam ao usuario como a mesma frase — apontando para credencial e
  bucket, causa em apenas duas delas.
- O corpo do `PUT` vai em **streaming** pelo descritor do arquivo. Antes o
  arquivo inteiro era carregado em memoria com `file_get_contents`, o que
  estourava o `memory_limit` em fotos grandes.
- A assinatura SigV4 foi extraida para um unico metodo, usado por `upload`,
  `delete` e pelo novo `exists`.
- O Canonical URI passou a ser **percent-encoded** preservando as barras.
  Qualquer chave com espaco ou acento gerava `SignatureDoesNotMatch`.
- Transporte fixado em TLS 1.2 minimo, HTTP/1.1 e IPv4, com `CONNECTTIMEOUT` de
  10s. Uma segunda tentativa cobre falha de transporte; erro de HTTP nao e
  repetido, porque `401` e `403` nao melhoram com insistencia.

### `api/lib/Storage.php`

- A mensagem devolvida ao navegador carrega o motivo real; o status virou `502`,
  que descreve melhor uma falha de servico externo.
- `storage_public_url()` codifica o caminho — para as chaves geradas por
  `uniqid()` nao muda nada, entao os registros antigos seguem validos.
- `storage_diagnostico()` executa o round-trip completo, confere o formato do
  account id, coleta as versoes de PHP/curl/OpenSSL e sonda o handshake em cinco
  combinacoes de transporte. Quando nenhuma fecha, aponta o `R2_ACCOUNT_ID` como
  suspeito — foi exatamente o caso aqui, e um id de outra conta passa no teste de
  formato.

### `api/admin/diagnostico_r2.php` (novo)

Endpoint restrito ao administrador do sistema. Ver secao proxima.

### `api/galerias/upload_capa.php`

- Os seis codigos de `UPLOAD_ERR_*` viraram mensagens distintas. A anterior
  ("tente uma imagem menor") era um chute: em quatro dos seis o tamanho nao tem
  relacao com a recusa.
- `foto_id` vazio nao e mais confundido com "promover a foto de id 0".
- **A capa avulsa nao recebe mais o selo `is_capa`.** O `UPDATE ... WHERE
  caminho_arquivo = <url da capa>` que existia ali nunca casava com nada: a capa
  avulsa nao tem linha em `imagens`.
- A capa avulsa anterior e removida do bucket ao ser substituida — antes virava
  lixo permanente. So quando o arquivo nao e tambem uma foto da galeria.
- Arquivo de 0 bytes e recusado antes de subir.

### `api/galerias/get.php`

`capa_preview` de uma capa avulsa cai para o proprio arquivo. Sem isso a consulta
por miniatura devolvia `NULL` e a previa sumia ao recarregar a pagina.

### `api/fotos/process_thumbs.php`

- O download do original passou de `@file_get_contents` para curl com o motivo da
  falha: `403` (acesso publico desligado), `404`, erro de rede e arquivo vazio
  agora sao distinguiveis. A verificacao de certificado, que estava desligada,
  voltou.
- Registros legados apontando para `uploads/` sao descartados com motivo proprio.
  Antes o caminho derivado saia deformado (`https:/uploads/...`) e a foto voltava
  para a fila ate esgotar as tres tentativas.
- Falhas de Imagick, de GD e do envio ao R2 gravam cada uma o seu motivo.

### `galeria.html`

"Previa indisponivel" aparecia tanto quando a galeria ainda nao tinha capa
(situacao normal) quanto quando o arquivo nao carregava (erro). O estado vazio
agora diz "Nenhuma capa definida". O seletor de arquivo passou a aceitar
exatamente os formatos que o servidor aceita (JPG, PNG, WEBP, GIF).

## O endpoint de diagnostico

`/api/admin/diagnostico_r2.php`, aberto no navegador logado como administrador do
sistema (conta em `ADMIN_EMAILS`).

Percorre o mesmo caminho de um upload real e devolve, em ordem:

1. **`configuracao`** — bucket, account id, endpoint, URL publica, prefixo da
   access key e variaveis ausentes.
2. **`ambiente`** — versoes de PHP, curl e OpenSSL do container. Um
   `handshake failure` quase sempre se explica por uma dessas linhas, e nenhuma e
   visivel de fora.
3. **`transporte`** — handshake TLS em cinco combinacoes (padrao, IPv4, TLS 1.2,
   a combinacao que o app usa, e sem verificar certificado). Qualquer codigo HTTP
   significa handshake concluido; o R2 responde `400` a um GET sem assinatura.
   Se `padrao` falha e outra passa, a que passou aponta a trava necessaria. Se
   **nenhuma** passa, o host nao existe — suspeite do account id.
4. **`etapas`** — formato do account id, `PUT` assinado, `HEAD` assinado, leitura
   pela URL publica e `DELETE`, cada uma com codigo HTTP e causa concreta.

Grava e apaga um PNG de 70 bytes em `diagnostico/`. Nao altera mais nada.
